## 1. 課題の概要

### 1.1 何を作るか
テーブル上に色・大きさの異なるブロック（3〜4個）と箱（2個）があるシーンで、
**日本語の自然言語指示**を受け取り、ロボットアーム（Franka Panda）が自律的にタスクを実行するシステム。

| 指示の例 | ロボットの動作 |
|---|---|
| 「赤いブロックを左の箱に入れて」 | 赤を掴む → 左の箱へ置く |
| 「青いもの以外を全部右の箱へ」 | 対象を列挙 → 順に運ぶ |
| 「大きい順に積み上げて」 | 大きさでソート → 下から積む |
| 「机の上を片付けて」 | 曖昧な指示を解釈 → 全ブロックを箱へ |
| 「緑のブロックを取って」（緑が無い） | 実行不能と判断して理由を返す |

### 1.2 目的
- 曖昧な人間の言葉を、**検証可能な**ロボット動作に変換する仕組みを作る
- 家庭の片付け・物流の仕分けなど、現実の応用を想定した構成にする
- 失敗しても自分で気づいて立て直す（**閉ループ**）ことを示す

### 1.3 課題要件との対応
| 課題要件 | 本設計での対応 |
|---|---|
| ロボットシミュレータを使用 | MuJoCo（物理シミュレータ） |
| AIの使用が必須（推論のみ可） | Gemini による行動計画・成功条件の生成（推論のみ） |
| タスクは自由設定 | 言語指示による片付け・仕分け・積み上げ |
| 動画 1〜3分 | 録画機能を内蔵、字幕で計画を可視化 |
| コード一式 | GitHub Public リポジトリ |
| レポート | 評価結果・工夫点・考察を PDF 化 |

> **【学習メモ】要件定義（第1回 MLOps・RobOps）**
> 第1回で「要件を数値化した管理指標に落とす」ことを学びました。本課題では
> 「成功率」「LLM呼び出し回数」「1タスクあたりのコスト」を管理指標にします（→ 7章）。

## 3. システム構成

### 3.1 全体アーキテクチャ

```
 ┌─────────┐   ┌──────────────┐
 │ 指示文   │   │ シーン状態     │ ← sim.get_state()（＋観測ノイズ）
 └────┬────┘   └──────┬───────┘
      └───────┬───────┘
              ▼
     ┌──────────────────┐
     │ Planner (Gemini)  │  出力: { plan: [スキル列], goal: [成功条件], feasible }
     └────────┬─────────┘
              ▼
     ┌──────────────────┐  NG（存在しない物体・不正な引数）
     │ Validator         │──────────────┐
     └────────┬─────────┘               │
              ▼ OK                       │
     ┌──────────────────┐               │
     │ Executor          │ スキル → IK → 軌道補間 → MuJoCo 制御
     └────────┬─────────┘               │
              ▼                          │
     ┌──────────────────┐  失敗（理由つき）│
     │ Verifier          │──────────────┤
     └────────┬─────────┘               ▼
              ▼ 成功            再計画（最大3回）→ Planner へ
       ログ(JSONL) + 録画(mp4)
```

### 3.2 モジュール一覧

| モジュール | ファイル | 責務 |
|---|---|---|
| Sim | `src/sim.py` | シーン生成（ランダム配置）、状態取得、外乱注入、録画 |
| IK | `src/ik.py` | 減衰最小二乗（DLS）IK、関節空間の軌道補間 |
| Skills | `src/skills.py` | `pick` / `place_in` / `stack_on` / `push` / `go_home` |
| Planner | `src/planner.py` | プロンプト生成、Gemini 呼び出し、JSONスキーマ、トークン計測 |
| Validator | `src/validator.py` | 計画の静的チェック（物体の存在、引数の型、前提条件） |
| Verifier | `src/verifier.py` | 成功条件（述語）をシミュレータ状態で判定 |
| Runner | `src/run.py` | 1指示を実行する CLI（`--record` で動画） |
| Eval | `eval/evaluate.py` | 指示 × seed × 条件 の一括評価 → CSV / グラフ |

> **【学習メモ】なぜ層を分けるのか（第7回 実運用）**
> 第7回で「失敗の切り分けは データ / 学習 / 推論 / 制御 の層ごとに」と学びました。
> モジュールを分けておくと、失敗が「計画の誤り（Planner）」「到達できない（IK）」
> 「掴めない（Skills）」「判定ミス（Verifier）」のどれかをログから特定できます。

## 4. シミュレーション環境（Sim）

### 4.1 シーン構成
| 要素 | 内容 |
|---|---|
| ロボット | Franka Emika Panda（7自由度＋2指グリッパ）。mujoco_menagerie のモデルを使用 |
| テーブル | 高さ約 0.4 m の平面 |
| ブロック | 立方体 3〜4個。色（赤・青・緑・黄）×大きさ（S: 4cm / L: 5cm） |
| 箱 | 左右に2個（壁つきトレイ） |
| カメラ | 正面斜め上（動画用）、真上（デバッグ用） |

### 4.2 状態表現（Planner に渡す JSON）
```json
{
  "objects": [
    {"id": "red_cube",  "color": "red",  "size": "large", "pos": [0.52, -0.10, 0.43], "in": null},
    {"id": "blue_cube", "color": "blue", "size": "small", "pos": [0.45,  0.12, 0.42], "in": null}
  ],
  "bins": [
    {"id": "left_bin",  "pos": [0.40,  0.30, 0.40]},
    {"id": "right_bin", "pos": [0.40, -0.30, 0.40]}
  ],
  "gripper": {"holding": null}
}
```
- 位置はシミュレータの真値に **ガウスノイズ（σ=5mm）** を加える（認識誤差の模擬）
- 拡張案：真値の代わりにカメラ画像を Gemini に渡して物体認識させる（時間が余れば）

### 4.3 外乱注入
評価条件③で、実行中にランダムなブロックへ水平方向の力を加えて位置をずらす。
→ 「計画通りに動いたのに結果が違う」状況を作り、再計画の効果を測る。

> **【学習メモ】MuJoCo の基本構造**
> - `MjModel`：変わらない情報（形状・質量・関節範囲）。MJCF（XML）から読み込む
> - `MjData`：変わる情報（関節角 `qpos`、速度 `qvel`、制御入力 `ctrl`）
> - `mj_step(model, data)`：物理を1ステップ（既定 2ms）進める
> - `mj_forward`：時間を進めずに位置・ヤコビアン等だけ再計算する
> この「モデル（静的）とデータ（動的）の分離」は多くのシミュレータに共通する設計です。

## 5. ロボット制御（IK・Skills）

### 5.1 逆運動学（IK）：減衰最小二乗法（DLS）
手先の目標位置・姿勢 → 関節角 を求める。

```
誤差     e  = [目標位置 − 現在位置 ; 姿勢誤差]          (6次元)
ヤコビアン J = ∂(手先位置・姿勢)/∂(関節角)              (6×7, mj_jacSite で取得)
更新量   Δq = Jᵀ (J Jᵀ + λ² I)⁻¹ e                       (λ: 減衰係数)
q ← q + α Δq  を誤差が閾値以下になるまで反復
```
- **なぜ「減衰」か**：特異姿勢（腕が伸び切る等）付近で J Jᵀ が逆行列を持たなくなり、
  普通の擬似逆行列では Δq が発散する。λ² I を足すことで安定させる
- 姿勢は「グリッパが真下を向く」で固定し、手首まわりの回転（yaw）だけ物体に合わせる

### 5.2 軌道生成
- IK で求めた目標関節角まで、**関節空間で線形補間**（最小躍度補間は拡張）
- Panda の位置制御アクチュエータに `ctrl` として与える

### 5.3 スキル定義
| スキル | 引数 | 動作 | 前提条件 |
|---|---|---|---|
| `pick(obj)` | 物体ID | 上空へ移動 → 下降 → 把持 → 上昇 | 何も持っていない |
| `place_in(obj, bin)` | 物体ID, 箱ID | 箱上空へ → 下降 → 開放 → 上昇 | `obj` を持っている |
| `stack_on(obj, base)` | 物体ID, 土台ID | 土台の上空へ → 下降 → 開放 | `obj` を持っている, `base` の上が空 |
| `push(obj, dir, dist)` | 物体ID, 方向, 距離 | 物体の横から押す | 何も持っていない |
| `go_home()` | なし | 初期姿勢に戻る | なし |

各スキルは `SkillResult(ok: bool, reason: str)` を返す。
例：`ok=False, reason="grasp_failed: red_cube not between fingers"`

### 5.4 把持方式（リスク対策つき）
1. **既定：摩擦による物理把持**（指の摩擦係数・ブロック質量を調整）
2. **代替：吸着モード**（把持判定時に weld 拘束を有効化）
   - 物理把持が安定しない場合の撤退策。使った場合はレポートに明記する

> **【学習メモ】なぜスキル（プリミティブ）に分けるのか**
> LLM に関節角を直接出させるのは不安定で危険です。LLM には「何をするか（What）」だけを決めさせ、
> 「どう動くか（How）」は検証済みのスキルが担う、という分担は SayCan や Code as Policies などの
> 研究でも採られている基本構成です（→ 参考文献）。第7回の「VLA ~10Hz → 制御 500Hz」という
> 階層構造と同じ発想で、**上位は遅く賢く、下位は速く確実に**動かします。

## 6. AI 部分（Planner / Validator / Verifier）

### 6.1 Planner：Gemini による計画生成
- モデル：Gemini Flash 系（低コスト・低遅延）
- **構造化出力（JSONスキーマ指定）**を使い、自由文ではなく必ず決まった形で返させる

出力スキーマ（概略）：
```json
{
  "feasible": true,
  "reasoning": "赤い物体は red_cube のみ。左の箱は left_bin。",
  "plan": [
    {"skill": "pick",     "args": {"obj": "red_cube"}},
    {"skill": "place_in", "args": {"obj": "red_cube", "bin": "left_bin"}}
  ],
  "goal": [
    {"pred": "in", "args": ["red_cube", "left_bin"]}
  ]
}
```
- `goal`（成功条件）も LLM に出させるのがポイント → 指示の「意味」を検証可能な形にする
- プロンプトには：スキル一覧と前提条件、シーン状態JSON、（再計画時は）前回の計画と失敗理由

### 6.2 Validator：実行前の静的チェック
- 存在しない物体ID・箱ID、未定義スキル、引数不足を検出
- 前提条件のシミュレーション（「持っていないのに place」など）
- NG なら実行せずに、理由を添えて即再計画（ロボットを無駄に動かさない）

### 6.3 Verifier：実行後のゴール判定
| 述語 | 判定方法 |
|---|---|
| `in(obj, bin)` | 物体中心が箱の内側領域にある |
| `on(obj, base)` | 物体の xy が土台の上で、z が土台上面＋半辺長付近 |
| `on_table(obj)` | 物体の z がテーブル高さ付近 |
| `holding(obj)` | 指の間に物体がある |

- LLM が出した `goal` に加え、**指示ごとの正解ゴール**（評価用、LLMには見せない）でも判定する
  → 「LLM が誤ったゴールを立てて自己満足する」ケースを検出できる

### 6.4 再計画ループ
```
for attempt in 1..3:
    result = planner(指示, 状態, 履歴)
    if not result.feasible: 拒否理由を返して終了
    if validator NG: 履歴に追加して continue
    スキルを順に実行（失敗したらその時点で中断）
    if verifier OK: 成功で終了
    履歴に「計画・失敗したスキル・理由・現在の状態」を追加
失敗で終了
```

> **【学習メモ】LLM の出力は「信用しないで検証する」**
> 第7回で「コーディングエージェントは評価をごまかす方向に進み得るので出力は必ず検証」と
> ありました。ロボットでも同じで、LLM の計画は **Validator（実行前）** と
> **Verifier（実行後）** の二重チェックを通します。これが Inner Monologue 等で
> 提案された「環境からのフィードバックで LLM の計画を修正する」考え方です。

## 7. 評価設計

### 7.1 指示セット（6種類）
| ID | 種類 | 指示文 | 難しさ |
|---|---|---|---|
| T1 | 単純移動 | 赤いブロックを左の箱に入れて | 低 |
| T2 | 属性による選択 | 小さいブロックを全部右の箱へ | 中 |
| T3 | 否定 | 青以外のブロックを左の箱に | 中 |
| T4 | 積み上げ | 大きい順に3段積んで | 高（精度が必要） |
| T5 | 曖昧 | 机の上を片付けて | 中（解釈が必要） |
| T6 | 実行不能 | 紫のブロックを取って | 拒否できれば成功 |

### 7.2 実験条件
| 条件 | 再計画 | 外乱 |
|---|---|---|
| A | なし（1回だけ計画） | なし |
| B | あり（最大3回） | なし |
| C | あり（最大3回） | あり |

- 各条件 × 各指示 × **10 seed**（初期配置をランダム化、seed は固定して再現可能に）

### 7.3 指標
- **成功率**（評価用の正解ゴールで判定）
- 平均 LLM 呼び出し回数、平均計画時間（秒）
- 入出力トークン数 → 1タスクあたりの推定コスト
- 失敗原因の内訳（計画 / Validator / IK / 把持 / 判定）

> **【学習メモ】再現可能な評価（第2回・第7回）**
> 第2回で「loss だけで判断しない。固定 seed 複数でシミュレータ評価し success rate を見る」、
> 第7回で TRI LBM の評価設計（初期条件の共有、何を測れていないかの明記）を学びました。
> LLM は同じ入力でも出力が揺れるため、**seed 固定・試行回数・条件比較**が特に重要です。
> レポートには「何を測れていないか」（例：実機での把持、実カメラでの認識）も書きます。

## 9. 技術選定とその理由
| 項目 | 選定 | 理由 | 却下した案 |
|---|---|---|---|
| シミュレータ | MuJoCo 3.x | Windows で pip だけで動く。接触物理が高品質。オフスクリーン録画が容易 | Gazebo + ROS 2（環境構築に時間がかかる）、Genesis（独自性を出しにくい） |
| ロボット | Panda（menagerie） | 実在ロボットの高品質モデル。研究でも標準的 | 自作アーム（把持の調整が大変） |
| LLM | Gemini Flash 系 | 低コスト・高速・構造化出力対応・無料枠あり | Claude（Maxプランでは API キーが使えない） |
| IK | 自前 DLS 実装 | 学習効果が高い。依存が少ない | mink 等のライブラリ（拡張時に比較対象として検討） |

## 10. リスクと対策
| リスク | 影響 | 対策 |
|---|---|---|
| 物理把持が安定しない | 成功率が低い | 摩擦・質量・把持力の調整 → ダメなら吸着モードへ（撤退ライン：11/1 10時） |
| IK が収束しない／関節限界 | 動作不能 | 作業領域を Panda の得意範囲に限定、反復回数・λ の調整 |
| Gemini 無料枠のレート制限 | 評価が止まる | 呼び出し間の待機、指数バックオフでリトライ |
| LLM の出力が揺れる | 結果の再現性が低い | temperature=0、構造化出力、seed ごとに複数試行 |
| 時間不足 | 提出不能 | 実装計画の撤退ラインに従い範囲を縮小 |
| 個人情報の映り込み | 規約違反 | 動画・レポートには Omnicampus アカウントIDのみ記載 |

## 用語集
| 用語 | 意味 |
|---|---|
| MJCF | MuJoCo のモデル記述形式（XML） |
| IK（逆運動学） | 手先の目標位置から関節角を求める計算 |
| ヤコビアン | 関節角の微小変化と手先の微小変化の関係を表す行列 |
| DLS | Damped Least Squares。特異点に強い IK 解法 |
| スキル／プリミティブ | 「掴む」「置く」など、検証済みの基本動作の単位 |
| 構造化出力 | LLM の出力形式を JSON スキーマで強制する機能 |
| 閉ループ | 実行結果を観測してフィードバックする制御・計画の形 |
| 述語（predicate） | `in(a, b)` のように真偽で判定できる条件 |
