## Step 1. 環境構築（10/31 夜・1h）

### 作業
1. Python 仮想環境を作成（OneDrive などの同期フォルダの外に置いたリポジトリ直下の `.venv`）
2. パッケージ導入：`mujoco`, `numpy`, `imageio[ffmpeg]`, `google-genai`, `matplotlib`, `pandas`
3. mujoco_menagerie から `franka_emika_panda` だけを取得（sparse checkout）
4. Panda を読み込んで静止画を1枚レンダリング
5. `git init`、`.gitignore`（`.venv/`, `outputs/`, `.env`）を作成

### 🎯 学習目標
- 依存関係を `requirements.txt` で固定し、他人の PC で再現できる状態にする（第2回・第4回）

### ✅ 完了条件
- `python -m src.sim --snapshot` で Panda の画像が `outputs/` に保存される

### 🔍 自分で確かめること
- なぜ仮想環境を OneDrive の外に置くのか？（ヒント：同期・パス・ファイル数）
- `requirements.txt` でバージョンを固定しないと何が起きるか？

## Step 2. シーン・IK・スキル（10/31 夜・2h）

### 作業
1. `assets/scene.xml`：テーブル、ブロック4個、箱2個、カメラ2台を Panda の MJCF に追加
2. `src/sim.py`：seed から初期配置をランダム生成、状態 JSON の取得、外乱注入、録画
3. `src/ik.py`：DLS IK（`mj_jacSite` でヤコビアン取得）、関節空間の線形補間
4. `src/skills.py`：`pick` / `place_in` / `stack_on` / `go_home`（`push` は余裕があれば）
5. 手書きのスキル列で「赤 → 左の箱」を実行して動画を保存

### 🎯 学習目標
- MuJoCo の `MjModel` / `MjData` / `mj_step` の関係を理解する
- ヤコビアンと DLS による IK を、式とコードの両方で説明できるようになる

### ✅ 完了条件
- LLM なしで、10 seed 中 8 回以上 pick & place に成功する
- 失敗時に `SkillResult(ok=False, reason=...)` が理由つきで返る

### 🔍 自分で確かめること
- 減衰係数 λ を 0 に近づける／大きくすると、動きはどう変わるか？（実際に試す）
- 把持が失敗する原因はどれか？：摩擦係数／把持力／下降位置の誤差／物体の質量
- 「上空へ移動 → 下降」と 2 段階にするのはなぜか？

## Step 3. AI 部分（11/1 午前・2h）

### 作業
1. `src/planner.py`
   - システムプロンプト：役割、スキル一覧と前提条件、出力ルール
   - Gemini の構造化出力（JSON スキーマ）で `feasible` / `reasoning` / `plan` / `goal` を受け取る
   - `temperature=0`、トークン数・応答時間をログに記録
   - レート制限対策：指数バックオフでリトライ
2. `src/validator.py`：物体 ID の存在、引数、前提条件（「持っていないのに置く」等）を検査
3. `src/verifier.py`：述語 `in` / `on` / `on_table` / `holding` の判定
4. `src/run.py`：再計画ループ（最大3回）、`--instruction`, `--seed`, `--record`, `--no-replan`, `--disturb`
5. API キーは環境変数 `GEMINI_API_KEY` から読む（**コード・リポジトリに絶対に書かない**）

### 🎯 学習目標
- 「LLM に何を決めさせ、何を決めさせないか」の設計判断を説明できる
- 構造化出力・検証・フィードバックで LLM の不確実さを抑える方法を理解する

### ✅ 完了条件
- 6種類の指示（設計書 7.1）のうち 4 種類以上が seed=0 で成功
- 実行不能な指示（T6）で `feasible=false` と理由が返る

### 🔍 自分で確かめること
- プロンプトからスキルの前提条件を消すと、計画の質はどう変わるか？
- LLM が出す `goal` と評価用の正解ゴールが食い違ったケースはあったか？それはなぜか？
- 再計画時に「失敗理由」を渡す／渡さないで、2回目の計画はどう変わるか？

## Step 4. 評価（11/1 昼・1.5h）

### 作業
1. `eval/evaluate.py`：指示 6 × seed 10 × 条件 A/B/C を一括実行 → `outputs/results.csv`
2. 集計：成功率、平均 LLM 呼び出し回数、平均計画時間、トークン数、推定コスト
3. 失敗原因の内訳（計画 / Validator / IK / 把持 / 判定）を集計
4. グラフ：条件別の成功率（指示ごとの棒グラフ）

### 🎯 学習目標
- seed 固定・条件比較による、再現可能な評価を自分で設計・実行できる（第2回・第7回）

### ✅ 完了条件
- `results.csv` と成功率のグラフ（PNG）ができ、README に貼れる

### 🔍 自分で確かめること
- 再計画（A → B）で一番改善した指示はどれか？それはなぜか？
- 外乱（B → C）で成功率が下がった指示は？再計画で回復できなかった理由は？
- この評価で **測れていないこと** は何か？（例：実機、実カメラ認識、未知の物体）
